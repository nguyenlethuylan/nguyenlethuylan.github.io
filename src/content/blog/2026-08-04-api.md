# S001: Understanding APIs: A Comprehensive Guide to Modern Protocols

An Application Programming Interface (API) lets different systems talk to each other, share data, and run processes. Choosing the right API style for your project matters a lot — it affects speed, security, and how easy the system is to scale.

This guide covers 7 common API styles, what makes each one different, and when to use them.


## 1. REST
*(Representational State Transfer)*

REST is a set of design rules, not a strict protocol. It runs on standard HTTP and treats everything in the system as a "resource," each with its own URL.

* **Key Characteristics:**
  * **Stateless:** The server does not remember anything about the client between requests. Each request must carry all the information it needs.
  * **Standard HTTP Methods:** Uses common verbs like `GET` (read), `POST` (create), `PUT/PATCH` (update), and `DELETE` (remove).
  * **Flexible Payload:** It can return XML or plain text, but **JSON** is what most people use today.
* **Best For:** Everyday web services and basic CRUD (Create, Read, Update, Delete) apps.
> **Example:** Getting a list of employees with `GET /api/v1/employees`, or removing one with `DELETE /api/v1/employees/123`.

## 2. SOAP
*(Simple Object Access Protocol)*

SOAP is older than REST and much stricter. It was first built by Microsoft and later standardized by the W3C. It's still common in industries where rules and security matter more than speed.

* **Key Characteristics:**
  * **Strict Contract:** Needs a WSDL (Web Services Description Language) file, so both sides know exactly what data to expect.
  * **XML Only:** Always uses XML — no other format.
  * **High Reliability:** Built-in support for strong data consistency (ACID) and advanced security (WS-Security).
* **Best For:** Banking systems, telecom, and older enterprise software where data accuracy is critical.

## 3. gRPC
*(gRPC Remote Procedure Calls)*

Built by Google, gRPC lets one system call a function on another system almost like calling a local function — instead of just fetching a URL.

* **Key Characteristics:**
  * **Protocol Buffers (Protobuf):** Packs data into a small binary format, so it's light and fast to send.
  * **Built on HTTP/2:** Supports multiple requests at once and two-way streaming.
  * **Low Latency:** Faster than REST because payloads are smaller and connections stay open.
* **Best For:** Communication between internal microservices (e.g., parts of a backend talking to each other) where speed matters most.

## 4. GraphQL

Created by Facebook, GraphQL lets the client ask for exactly the data it needs — nothing more, nothing less.

* **Key Characteristics:**
  * **Single Endpoint:** All requests go to one URL (usually `POST /graphql`).
  * **No Over- or Under-fetching:** Fixes the common REST problem of calling many endpoints or getting back too much unused data.
  * **Typed Schema:** The server defines exactly what data is available and its type.
* **Best For:** Mobile apps and complex web apps where saving bandwidth and getting precise data matters.

## 5. WebHook

A WebHook is sometimes called a "reverse API." Instead of the client repeatedly asking the server "any updates?" (polling), the server sends data to the client automatically when something happens.

> Note: A WebHook is not really a separate protocol like the others on this list — it's a simple pattern built on top of regular HTTP requests. It's included here because it's such a common way for systems to talk to each other.

* **Key Characteristics:**
  * **Push-based:** Data flows one way, from server to client.
  * **Event-Driven:** Only sends data when a specific event happens.
  * **Saves Resources:** No need to keep asking the server for updates.
* **Best For:** Payment alerts (e.g., Stripe notifying you a payment succeeded), CI/CD pipelines, and automated notifications.

## 6. WebSocket

A WebSocket keeps one connection open between client and server, so both sides can send messages back and forth at any time, without opening a new connection each time.

* **Key Characteristics:**
  * **Stays Connected:** The server keeps the connection open and knows the client.
  * **Two-Way:** Both sides can send messages at the same time, with less overhead than regular HTTP.
  * **Real-Time:** Very low delay, good for constant data flow.
* **Best For:** Live chat apps, real-time stock or crypto dashboards, and online multiplayer games.

## 7. WebRTC
*(Web Real-Time Communication)*

WebRTC lets two browsers or apps talk directly to each other (peer-to-peer), without sending data through a central server.

* **Key Characteristics:**
  * **Peer-to-Peer:** Data goes straight from one device to another, which keeps delay low.
  * **Needs a Little Setup First:** Before the direct connection starts, both sides usually need a small "introduction" step (often using STUN, TURN, and ICE) to find each other and get through firewalls or routers. After that, the data flows directly.
  * **Mostly Uses UDP:** UDP is faster but can drop a few packets — an acceptable trade-off for real-time video and audio.
  * **Built for Media:** Designed to handle audio, video, and other real-time data.
* **Best For:** In-browser video calls (e.g., Google Meet, Zoom Web) and direct file sharing between two users.

## 8. Summary & Comparison Table

Use this table as a quick reference:

| API Style | Runs On | Data Format | Main Strength | Best For |
| :--- | :--- | :--- | :--- | :--- |
| **REST** | HTTP/1.1 | JSON, XML | Simple, easy to scale | Standard web APIs, CRUD |
| **SOAP** | HTTP, SMTP | XML | Strong security & reliability | Banking, legacy enterprise systems |
| **gRPC** | HTTP/2 | Binary (Protobuf) | Very fast | Microservices, backend-to-backend |
| **GraphQL** | HTTP | JSON | Precise, no wasted data | Mobile apps, complex UIs |
| **WebHook** | HTTP | JSON | Saves resources | Payment alerts, CI/CD |
| **WebSocket** | TCP | Text, Binary | Real-time, two-way | Chat apps, live dashboards |
| **WebRTC** | Mainly UDP (TCP as backup) | Media streams | Low-delay, peer-to-peer | Video calls, live streaming |

> **In short:** there's no single "best" API. The right choice depends on what you need — how fast it must be, how secure it must be, how much data you're sending, and how the systems involved need to talk to each other.
